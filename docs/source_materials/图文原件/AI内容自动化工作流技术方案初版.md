# 1. 项目定位
本项目定位为一套面向内容运营场景的 **AI内容自动化工作流系统**，核心链路为 **热点发现—链接解析—品牌融合—多模态生成—审核协同—自动分发—数据回流**。

该系统不是普通的 AI 写文案工具，也不是单纯的爬虫系统，而是将内容采集、内容理解、品牌信息注入、图文/视频生成、人工审核、平台分发和效果回流整合为统一流程的内容生产系统，目标是在保证内容质量和品牌一致性的前提下，提高内容生产效率，降低人工重复投入，形成可持续优化的内容生产闭环。

# 3. AI内容自动化业务流程

# 4. 多源头数据采集模块
## 4.1 模块目标
多源头数据采集模块只解决一个问题：素材从哪里来。

该模块负责把外部平台上的热点内容、搜索结果和可跟踪账号持续采集进系统，并整理为后续模块可直接使用的标准化输入。模块运行采用“主动监测 + 被动搜索”双模式。主动监测用于持续抓取各平台热榜、趋势页和热门内容，保证系统能够及时发现新热点；被动搜索用于根据业务关键词、城市词和领域词执行定向抓取，补充业务指定方向的素材。

模块完成后，系统可以稳定获取标题、文案、链接、作者、互动量、封面图、视频地址或素材链接、发布时间、LBS 等基础信息，并把这些结果作为后续链接解析、品牌融合、多模态生成的统一素材来源。换句话说，第4章对应的是整个工作流的数据入口，没有这一层，后续生成链路就没有稳定输入。

## 4.2 技术实现与选型
本模块以 Python 为主实现语言，整体采用“抓取、清洗、标准化保存”的技术路线。当前实现不是单一采集方式覆盖所有平台，而是根据 YouTube、小红书、抖音、Bilibili 的页面结构、公开访问方式和字段暴露差异分别设计抓取策略，再将结果统一整理为标准化内容结构。

针对热榜抓取，当前采用 `Python + Playwright` 作为核心方案。Playwright 负责打开真实平台页面、等待前端渲染、执行滚动加载、定位 DOM 元素并提取热点内容字段。这一方案主要用于 YouTube、小红书、抖音这类前端渲染明显、列表内容依赖浏览器行为加载的平台。对于 Bilibili 这类页面结构相对稳定、公开字段较容易定位的平台，则在浏览器访问之外结合页面结构解析与公开请求访问，提升字段获取效率和结果稳定性。

针对关键词搜索，当前采用 `Python + requests + Playwright` 的组合方式。`requests` 负责关键词编码、搜索参数拼接和公开可访问请求的组织；Playwright 负责处理必须通过真实搜索页才能稳定获取的结果列表。这样处理后，关键词搜索与热榜抓取共用同一套字段提取和结果保存逻辑，搜索得到的内容可以直接进入后续过滤、账号识别和素材沉淀流程。

针对账号池跟踪，当前采用“内容结果反推账号”的实现方式。系统从热榜结果和搜索结果中提取作者名称、主页链接、账号标识和代表内容链接，并自动沉淀为账号记录。账号池不是独立维护的静态名单，而是由真实采集结果持续反哺生成。这样处理后，账号池既能作为高价值内容源的沉淀结果，也能作为后续定向跟踪采集的输入基础。

针对过滤和保存，当前采用 `Python + JSON 数据处理 + 文件存储` 的实现方式。原始抓取结果先统一整理为标准字段结构，再按平台分别执行阈值过滤。过滤逻辑以互动量字段为核心，不同平台按各自规则独立处理，避免单一阈值影响结果有效性。过滤后的内容、账号信息和素材清单分别保存，便于后续模块直接消费，也便于后续规则调优和结果回查。

针对元数据提取，当前已稳定覆盖标题、内容链接、作者名称、互动量、发布时间、封面图、主页链接等核心字段。对于可直接获取的封面资源，系统已经能够真实下载并保存到本地素材目录；对于页面未直接暴露的视频直链，则保留真实内容页地址、封面地址和素材状态说明，不做伪造补齐。现阶段结果主要以结构化文件形式落盘，已满足采集验证、链路联调和后续接入统一存储的需要。

从当前实现基础看，模块已经明确使用了 `Python`、`Playwright`、`requests`、页面结构解析、JSON 结果处理和文件存储等技术组件。技术路线已经形成，并且已经通过真实代码运行验证，不依赖概念性推演。

# 5. 品牌价值与视觉资产库
## 5.1 模块目标
品牌价值与视觉资产库不是单纯做文本分析，也不是把外部素材简单归档。该模块的任务是把固定产品参数与第4章已经获取的外部图文内容结合，提炼出可用于内容生成的品牌卖点，并将可复用的视觉素材整理为可调用的资产条目，为后续 AI 仿写提供“品牌灵魂”。

本次验证所使用的外部内容，明确来源于小红书关键词搜索结果，关键词为“新手开车技巧”。在这一前提下，模块不再重复做平台抓取，而是直接读取已落盘的搜索结果，对标题、摘要、互动信息、封面图和本地素材路径进行解析，并与固定产品参数进行映射，输出品牌卖点库和视觉资产库。

因此，第5章对应的目标可以明确归纳为两项：一是将产品参数与外部内容中的用户痛点、表达模式和内容钩子结合，形成可供生成调用的品牌卖点条目；二是将搜索结果中的封面图、本地素材和风格线索整理为可入库、可检索、可调用的视觉资产条目。

## 5.2 技术实现思路
本模块的输入由两部分组成。第一部分是固定产品参数，当前最小验证中已定义结构化产品输入，包括产品名称、产品类型、核心卖点、目标人群、使用场景和品牌调性。第二部分是第4章已经采集并保存的小红书关键词搜索结果，关键词固定为“新手开车技巧”，当前真实样本为 5 条搜索结果。

在品牌卖点提炼方面，技术实现不是简单做词频统计，而是执行“外部内容解析 -> 用户痛点识别 -> 表达模式识别 -> 产品特征映射 -> 品牌卖点生成”五步处理。脚本首先读取搜索结果中的标题、摘要、互动字段和标签信息，识别“拿证后不敢上路”“具体驾驶动作不会处理”“缺少系统化教程”“担心驾驶不安全”等用户痛点；随后识别“保姆级教程”“最全教程”“技巧合集”“逼自己看完”“学会这几个”这类爆款表达方式和内容钩子；最后将这些内容与固定产品参数中的“一对一真实道路陪练”“场景化专项训练”“防御性驾驶训练”“分场景训练清单”等产品特征进行映射，生成结构化品牌卖点条目，写入品牌卖点库文件。

在视觉资产整理方面，技术实现围绕“封面图可用性 + 风格可迁移性 + 生成可调用性”展开。脚本读取小红书搜索结果中的 `cover_url`、本地封面素材路径、标题和摘要，结合素材清单中的 `asset_status` 与 `asset_reason`，为每条内容生成视觉资产条目。资产条目不仅保留封面图和本地路径，还进一步补充视觉风格标签、场景标签、内容类型和是否可直接用于生成参考。当前样本中已经可以稳定识别“知识教程型封面”“清单总结型封面”“结果承诺型封面”三类风格，以及“新手上路场景”“停车入库场景”等驾驶主题场景。

本次实现所使用的技术组件以 Python 为主，围绕结构化 JSON 读取、规则匹配、字段映射和文件落盘完成。当前最小验证脚本已经拆分为产品参数样例文件 `product_params.sample.json`、品牌卖点提炼脚本 `build_brand_selling_points.py`、视觉资产整理脚本 `build_visual_asset_library.py` 和主流程脚本 `run_brand_asset_pipeline.py`，输出结果分别形成 `brand_selling_points.json`、`visual_asset_library.json` 和 `brand_asset_summary.json`。技术上已经证明，第5章并不是对第4章结果做简单摘要，而是把“小红书关键词搜索：新手开车技巧”的真实结果转换成了后续生成链路可调用的品牌输入结构。

需要明确的是，原始需求中提到的 OpenClaw / 搜索引擎补充卖点提炼和飞书确认链路，当前最小验证尚未接入。本次验证先完成了“固定产品参数 + 小红书关键词搜索结果 -> 卖点库 -> 视觉资产库”的核心解析闭环，后续只需在此基础上增加外部补充源和飞书确认节点即可。

验证结果表明，当前链路已经能够完成三项关键能力。第一，能够把外部内容中的用户痛点转成品牌卖点条目，而不是停留在关键词层面。第二，能够把搜索结果中的封面图和本地素材整理成可入库、可分类、可调用的视觉资产条目。第三，能够将产品参数、外部内容和解析结果统一落盘，形成后续生成模块可直接使用的品牌输入。

当前验证也明确暴露了尚未完成的部分：当前视觉资产仍以封面图为主，尚未包含品牌 UI 截图、品牌宣传样图和品牌水印；当前卖点补充仍只基于已抓取的小红书搜索结果，尚未接入 OpenClaw 或搜索引擎执行全网补充卖点提炼；当前流程也尚未接入飞书确认环节。因此，本章已经验证的是“固定产品参数 + 小红书关键词搜索结果 -> 品牌卖点库 + 视觉资产库”的最小可运行闭环，而不是完整的品牌资产运营流程。

# 6. 多模态 AI 仿写与适配引擎

## 6.1 模块目标

多模态 AI 仿写与适配引擎是整套系统的核心处理层，负责将外部热点内容模板与内部品牌资产进行融合，输出可直接进入审核与分发环节的图文或视频成品。该模块不是简单重写文案，而是围绕原始内容的情感钩子、逻辑结构、排版方式、视觉节奏和平台语境，结合品牌卖点、品牌视觉素材和目标发布场景，完成内容级重构与适配。

该模块主要承担三类任务：一是文本层面的深度仿写，包括标题、正文、标签和表达风格迁移；二是图文与视频层面的多模态生成，包括配图生成、图文合成、视频生成与风格延续；三是平台场景化微调，包括字数限制、内容规范、平台语气以及高德 POI/LBS 等发布约束。最终输出目标不是草稿，而是具备实际发布价值的内容成品。

# 7. 人机协同与质控模块
## 7.1 模块目标

该模块不做复杂逻辑，只解决一个问题：
 在自动化生成流程中加入人工可控节点，保证内容质量可控、可回退、可调整。

核心作用是：
 在“自动生成”与“人工决策”之间建立一个简单、稳定的控制层。

## 7.2 技术实现思路
该模块的实现重点不在流程设计，而在于用最少的技术手段，把 AI 自动生成链路中的关键节点变成“可控节点”。整体实现采用“LLM 分析 + OpenClaw 调度 + 飞书交互”的组合方式，不引入额外复杂系统。

在内容质控部分，预评分与合规自检本质上是一次标准化的大模型调用。生成结果作为输入，通过统一的提示词模板完成结构化分析，输出内容相似度、卖点融合度和平台违规风险三个维度的评分结果。该过程不依赖自研算法或规则引擎，而是直接利用大模型的语义理解能力完成判断，并以 JSON 结构返回结果，供后续流程判断使用。这一部分技术实现非常轻量，属于典型的 LLM 二次分析应用。

在人机交互部分，系统不单独开发后台审核界面，而是直接使用飞书作为控制台，通过 OpenClaw 完成任务调度与消息触达。具体实现上，采集到的热点内容、生成后的图文或视频结果，均通过飞书卡片形式推送给人工节点，卡片中携带任务 ID、内容摘要和操作入口。用户在飞书内的操作（通过、重写、人工调整）通过回调接口或 Webhook 返回系统，由 OpenClaw 继续驱动后续流程执行。整个交互链路本质上是“消息推送 + 回调触发”，不涉及复杂状态机或前端交互系统。

从技术构成上看，该模块主要使用的能力包括：大模型文本分析能力（用于质量评分与合规判断）、OpenClaw 的任务编排与工具调用能力（用于串联流程）、以及飞书开放平台提供的消息卡片与回调接口（用于人机交互）。模块本身不承担内容生成或数据处理职责，而是作为轻量控制层嵌入在生成链路中。

整体实现的关键不在技术复杂度，而在于通过现有工具快速完成“自动生成 + 人工决策”的结合，使系统在保持自动化效率的同时具备可控性和可干预能力。
