# 6_1_口播数字人链路诊断与改造方案_v_1_0

## 1. 文档目标

本文用于梳理当前`口播数字人`链路的真实实现方式、存在的问题、改造优先级与逐项实施方案。

目标不是一次性重写，而是按阶段逐步提升四件事：

1. 生成质量
2. 生成速度
3. 可视化可用性
4. 工程稳定性

## 3. 当前主要问题

### 3.1 架构问题

#### 问题 1：核心生成流程过度前端直连

当前提取、改写、TTS、数字人生成都由前端直接请求`8002`服务。

问题：

- 前端承担过多业务编排
- 浏览器变成任务中转层
- 日志分散，排障困难
- 后续做权限、限流、重试、审计都不方便

影响：

- 稳定性差
- 多用户场景不可控
- 很难做企业级运维


#### 问题 2：前端二次下载再上传音视频，链路慢且脆弱

当前音频、视频生成结果不是服务端直传MinIO，而是：

`服务返回URL -> 浏览器下载Blob -> 浏览器再上传MinIO`

问题：

- 大文件走浏览器，速度慢
- 用户网络波动会影响成片成功率
- 浏览器内存占用大
- 手机/弱网/企业代理环境更容易失败


#### 问题 3：任务状态同步分散

当前数字人任务存在两套状态同步思路：

- 页面内自己处理
- `App.vue`全局轮询处理

相关位置：

- [CreationAvatarView.vue](/e:/AI内容自动化/frontend/src/views/CreationAvatarView.vue:2334)
- [frontend/src/App.vue](/e:/AI内容自动化/frontend/src/App.vue:171)

问题：

- 职责重复
- 容易出现状态不同步
- 后面扩展批量任务会更乱


### 3.2 生成质量问题

#### 问题 4：文案改写不是真正的口播脚本生成

当前改写指令只是简单拼接：

- 模板
- 语气
- 附加要求

位置：

- [CreationAvatarView.vue](/e:/AI内容自动化/frontend/src/views/CreationAvatarView.vue:1694)

而发送给模型的输入只有：

- `text`
- `instruction`

位置：

- [CreationAvatarView.vue](/e:/AI内容自动化/frontend/src/views/CreationAvatarView.vue:3046)

问题：

- 没有显式带入平台特征
- 没有明确时长目标
- 没有明确口播节奏
- 没有明确转化目标
- 没有明确数字人场景目标

结果：

当前更像“改写器”，不是“口播数字人脚本生成器”。


#### 问题 5：模型与TTS配置存在硬编码

当前前端直接写死：

- 复刻音色模型：`cosyvoice-v3.5-plus`
- TTS默认模型：`cosyvoice-v3-flash`

位置：

- [CreationAvatarView.vue](/e:/AI内容自动化/frontend/src/views/CreationAvatarView.vue:2670)
- [CreationAvatarView.vue](/e:/AI内容自动化/frontend/src/views/CreationAvatarView.vue:2789)

问题：

- 不符合多用户系统要求
- 无法按用户配置动态切换
- 无法统一从数据库模型配置读取


#### 问题 6：音频参数语义不严谨

当前TTS请求中：

- `volume` 使用的是 `voiceSimilarity`

位置：

- [CreationAvatarView.vue](/e:/AI内容自动化/frontend/src/views/CreationAvatarView.vue:2798)

这在语义上明显不合理。

问题：

- 相似度和音量不是一回事
- 容易导致声音效果异常
- 后面调优无从下手


#### 问题 7：草稿 `draft_id` 被错误转为数字

当前TTS请求中：

- `draft_id: draftId.value ? Number(draftId.value) : null`

位置：

- [CreationAvatarView.vue](/e:/AI内容自动化/frontend/src/views/CreationAvatarView.vue:2793)

问题：

- 草稿ID是字符串，例如`draft_xxx`
- `Number(draftId.value)`会变成`NaN`
- 这会污染后端任务记录或日志关联


#### 问题 8：输出比例判断依赖前端临时元数据

当前比例逻辑：

- 根据前端读到的素材宽高判断
- 一旦读不到，就默认回退到`9:16`

位置：

- [CreationAvatarView.vue](/e:/AI内容自动化/frontend/src/views/CreationAvatarView.vue:2152)

问题：

- 前端元数据未加载完成时容易误判
- 会造成横屏素材被错误按竖屏生成


### 3.3 数据与流程问题

#### 问题 9：草稿状态过粗，无法支撑可视化流程

当前草稿状态只大致区分：

- `draft`
- `extracted`
- `rewritten`

位置：

- [CreationAvatarView.vue](/e:/AI内容自动化/frontend/src/views/CreationAvatarView.vue:1755)

但实际链路已经包含：

- 文案提取完成
- 文案生成完成
- 音频生成完成
- 数字人任务提交
- 数字人视频生成完成
- 剪辑完成

问题：

- 草稿进度不真实
- 草稿箱展示不准确
- 后续做节点可视化会很难看


#### 问题 10：缺乏稳定的音频时间轴落库

当前口播页生成完音频后，没有形成一个稳定、结构化、可复用的逐句时间轴结果。

后续剪辑时，如果拿不到转录分段，就只能用整段文本平均切分。

相关后端逻辑：

- [backend/app/services/clip_render_service.py](/e:/AI内容自动化/backend/app/services/clip_render_service.py:740)
- [backend/app/services/clip_render_service.py](/e:/AI内容自动化/backend/app/services/clip_render_service.py:748)

问题：

- 字幕节奏不准
- 剪辑点不准
- 后续镜头节奏无法精细化


## 4. 目标状态

口播数字人改造后的目标链路：

1. 用户输入链接或文本
2. 主后端统一发起内容提取
3. 主后端统一调用LLM生成“口播脚本”
4. 主后端统一调用TTS生成音频
5. 主后端统一落库音频URL、时长、逐句时间轴
6. 主后端统一调用数字人生成服务
7. 生成结果由服务端直接同步到MinIO
8. 主后端统一更新任务状态与草稿状态
9. 前端只负责展示、编辑、重试和预览

目标原则：

- 浏览器不做大文件中转
- 模型配置从数据库动态读取
- 草稿状态真实反映生产流程
- 每个阶段都有可追踪日志
- 为后续批量生成打基础


## 5. 改造优先级

### P0：必须先改

1. 把提取/改写/TTS/数字人提交收回主后端
2. 去掉前端下载再上传MinIO的中转逻辑
3. 修复`draft_id`错误转数值
4. 去掉TTS硬编码模型
5. 修复`voiceSimilarity -> volume`参数混用
6. 统一任务状态同步机制

### P1：紧接着改

1. 把“改写”升级成“口播脚本生成”
2. 落库逐句时间轴
3. 重构草稿状态体系
4. 重构口播页的步骤可视化

### P2：后续持续优化

1. 模型选择接入真实可控链路
2. 支持多脚本风格模板
3. 支持A/B文案版本
4. 支持批量口播生成
5. 支持质量评分与失败原因分析


## 6. 建议实施顺序

### 第一阶段：先做链路收口

目标：

- 让主后端成为唯一编排层

要改的内容：

1. 新增主后端服务：
   - `extract_copy`
   - `generate_talk_script`
   - `generate_tts_audio`
   - `submit_digital_human_video`
   - `sync_generated_media_to_minio`

2. 前端不再直接请求`8002`
   - 前端只请求主后端

3. 主后端内部再请求AI服务或数字人服务

4. 服务端直接处理媒体回传MinIO

验收标准：

- 浏览器Network里不再直接出现`8002`核心生成调用
- 音频/视频不再经过浏览器Blob二次上传


### 第二阶段：重做文案生成逻辑

目标：

- 从“改写文本”升级为“生成适合数字人讲的口播脚本”

要改的内容：

输入不再只有：

- `text`
- `instruction`

而应包含：

- 来源平台
- 原始文案
- 标题/作者/内容结构
- 目标场景：口播数字人
- 目标风格
- 目标时长
- 目标语气
- 是否强调转化

输出建议结构：

```json
{
  "title": "脚本标题",
  "style": "自然讲解",
  "duration_target_seconds": 35,
  "full_script": "完整口播文案",
  "paragraphs": [
    {
      "seq": 1,
      "text": "第一段",
      "intent": "开场抓人"
    }
  ],
  "hook": "前3秒重点句",
  "cta": "结尾动作引导"
}
```

验收标准：

- 输出结果不再只是一个改写文本
- 能支撑后续TTS和剪辑


### 第三阶段：补齐音频结构化结果

目标：

- 音频不是只保存URL，而是保存可用于后续剪辑的完整结构

建议落库到`voice_params`中的内容：

```json
{
  "audio_url": "",
  "source_audio_url": "",
  "duration_seconds": 0,
  "voice_asset_id": 0,
  "voice_id": "",
  "style": "",
  "speed": 1.0,
  "timeline_segments": [
    {
      "start": 0.0,
      "end": 1.8,
      "text": "大家好，今天给大家介绍一下"
    }
  ]
}
```

验收标准：

- 每次生成音频后都能得到稳定的时间轴
- 剪辑模块不再依赖“均分文本”


### 第四阶段：重构草稿状态体系

目标：

- 让草稿状态真实反映口播数字人生产进度

建议状态：

- `draft`
- `copy_extracted`
- `script_generated`
- `voice_generated`
- `avatar_submitted`
- `avatar_generating`
- `avatar_generated`
- `clip_generated`
- `completed`
- `failed`

同时建议增加失败信息字段：

- `last_error_stage`
- `last_error_message`

验收标准：

- 草稿箱能准确显示当前进展
- 页面步骤能准确显示当前卡在哪一步


### 第五阶段：统一任务中心

目标：

- 数字人视频生成任务只保留一套状态管理机制

建议：

1. 主后端记录任务
2. 前端只读取主后端任务状态
3. `App.vue`全局轮询与页面局部轮询统一收口

验收标准：

- 同一个任务不会在多个地方重复维护状态
- 页面刷新后仍能恢复任务进度
