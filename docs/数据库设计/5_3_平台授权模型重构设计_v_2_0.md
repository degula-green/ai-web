# 5.3 平台授权模型重构设计 v2.0

## 1. 背景

当前平台授权已从“系统内扫码授权”演变为“CookieBridge 插件上传浏览器登录态”的模式。该模式能快速跑通发布与采集，但已经暴露出几个结构性问题：

1. 平台账号实体与浏览器登录态没有解耦。
2. 同一用户绑定多个抖音账号时，容易因默认昵称相同被合并。
3. 用户在本地浏览器切换账号后，平台侧无法及时感知“账号已切换”。
4. 发布链路与采集链路分别依赖不同绑定表，授权状态不一致时难以排障。
5. 前端容易看到“已授权”，但实际刷新作品、发布视频已经失败。

本次重构不放弃纯插件模式。插件仍然是本机登录态采集器，但不再充当账号身份真相源。

## 2. 重构目标

### 2.1 业务目标

1. 一个系统用户支持多个同平台账号并行使用。
2. 平台能够识别“当前登录态属于哪个平台账号”。
3. 用户在本地浏览器切号后，系统能自知并阻断错误操作。
4. 采集与发布统一依赖同一套账号实体和会话状态。
5. 前端展示的授权状态必须和真实可用性一致。

### 2.2 技术目标

1. 区分“账号实体”“授权会话”“插件来源”三层模型。
2. 引入账号身份校验机制，不再只信任 cookie 是否存在。
3. 允许会话变化，但账号身份必须稳定。
4. 支持平滑迁移，不要求一次性重建全部旧数据。

## 3. 当前模型问题分析

## 3.1 当前关键表

1. `platform_accounts`
2. `platform_account_sessions`
3. `platform_cookie_bridge_bindings`
4. `crawler_cookies_account`
5. `crawler_cookie_account_bindings`

## 3.2 当前实际问题

### 问题一：账号实体和浏览器状态混在一起

现有逻辑默认“当前 CookieBridge 上传的登录态 = 当前账号本身”。

后果：

1. 用户在浏览器中切换抖音号后，系统仍可能把新的 cookie 当作旧账号会话刷新。
2. 账号身份没有稳定主键时，只能按昵称、默认名称、历史绑定猜测。

### 问题二：默认昵称导致账号记录被复用

当前 CookieBridge 绑定常见默认名称为：

`抖音已登录账号`

如果没有及时提取稳定身份字段，不同抖音号可能被写入同一条 `platform_accounts` 记录。

### 问题三：发布链路和采集链路双轨制

1. 发布使用 `platform_accounts + platform_account_sessions`
2. 采集使用 `crawler_cookie_account_bindings + crawler_cookies_account`

后果：

1. 一套状态正常，另一套失效。
2. 平台授权中心显示正常，但刷新作品失败。

### 问题四：平台无法自知账号切换

用户在自己浏览器中：

1. 退出原账号
2. 登录另一个账号
3. 插件继续上传当前浏览器 cookie

服务器如果不做身份比对，只会认为“会话被刷新”，而不会认为“账号已切换”。

## 4. 新模型设计

重构后统一拆为三层。

### 4.1 第一层：平台账号实体

表示“这是哪个平台账号”。

这层必须绑定稳定身份，不能依赖昵称。

建议优先级：

1. `sec_user_id`
2. `platform_uid`
3. 其他平台稳定唯一标识

### 4.2 第二层：授权会话

表示“这个账号当前有没有可用登录态”。

会话是可变化的，但必须明确归属哪个账号实体。

### 4.3 第三层：插件来源

表示“这份登录态来自哪个 CookieBridge 客户端/浏览器实例”。

这层只记录来源，不负责定义账号身份。

## 5. 数据表改造方案

## 5.1 `platform_accounts` 改造

现有表继续保留，增强字段。

### 新增字段建议

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `identity_type` | VARCHAR(32) | 账号主身份类型，如 `sec_user_id` |
| `identity_value` | VARCHAR(255) | 主身份值 |
| `sec_user_id` | VARCHAR(255) | 抖音稳定身份 |
| `account_status` | VARCHAR(32) | 账号状态 |
| `last_identity_verified_at` | DATETIME | 最近一次身份校验时间 |
| `last_identity_error` | VARCHAR(500) | 最近一次身份校验失败原因 |

### 状态枚举建议

1. `active`
2. `expired`
3. `account_mismatch`
4. `needs_rebind`
5. `disabled`

### 唯一约束建议

优先增加：

`UNIQUE KEY uk_owner_platform_secuid (owner_user_id, platform_code, sec_user_id)`

若平台没有 `sec_user_id`，则退化为：

`UNIQUE KEY uk_owner_platform_identity (owner_user_id, platform_code, identity_type, identity_value)`

## 5.2 `platform_account_sessions` 改造

该表继续作为“当前授权会话表”。

### 新增字段建议

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `session_status` | VARCHAR(32) | 会话状态 |
| `cookie_hash` | VARCHAR(128) | 当前 cookie 摘要 |
| `storage_hash` | VARCHAR(128) | localStorage 摘要 |
| `source_type` | VARCHAR(32) | 会话来源，当前为 `cookie_bridge` |
| `source_client_id` | VARCHAR(128) | 来源插件客户端 ID |
| `validated_identity` | VARCHAR(255) | 最近一次校验出的身份值 |
| `last_validation_error` | VARCHAR(500) | 最近一次会话校验错误 |

### 会话状态枚举建议

1. `active`
2. `invalid`
3. `expired`
4. `account_mismatch`

## 5.3 `platform_cookie_bridge_bindings` 改造

该表不再承担账号真相定义职责，只作为插件来源映射表。

### 字段定位

| 字段名 | 用途 |
| --- | --- |
| `bridge_client_id` | 来源浏览器客户端 |
| `platform_account_id` | 当前映射的平台账号 |
| `status` | 来源绑定状态 |
| `last_sync_at` | 最近一次插件同步时间 |

### 新增字段建议

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `last_reported_identity` | VARCHAR(255) | 插件最近上报的账号身份 |
| `last_reported_nickname` | VARCHAR(255) | 插件最近上报昵称 |
| `last_cookie_hash` | VARCHAR(128) | 最近一次 cookie 摘要 |

## 5.4 `crawler_cookies_account` 与 `crawler_cookie_account_bindings`

这两张表短期保留。

### 短期策略

1. 继续作为 crawler-engine 兼容层。
2. 由 `platform_account_sessions` 派生更新。
3. 不再让它们独立决定账号身份。

### 长期策略

逐步收敛为：

1. `platform_accounts`
2. `platform_account_sessions`
3. crawler 使用派生后的 cookie 数据，不再维护一套“平行账号体系”。

## 5.5 新增账号身份快照表（可选）

建议新增：

`platform_account_identity_snapshots`

用途：

1. 记录每次插件上报的身份快照。
2. 排查“什么时候切号”“什么时候失效”。

建议字段：

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `owner_user_id` | BIGINT | 用户ID |
| `platform_code` | VARCHAR(32) | 平台 |
| `bridge_client_id` | VARCHAR(128) | 插件来源 |
| `platform_account_id` | BIGINT | 关联账号，可为空 |
| `identity_type` | VARCHAR(32) | 主身份类型 |
| `identity_value` | VARCHAR(255) | 主身份值 |
| `nickname` | VARCHAR(255) | 昵称 |
| `profile_url` | VARCHAR(1024) | 个人主页链接 |
| `cookie_hash` | VARCHAR(128) | cookie 摘要 |
| `reported_at` | DATETIME | 上报时间 |

## 6. 插件上报协议调整

当前插件不能只上传 cookie。

必须同时上传身份快照：

```json
{
  "platformCode": "douyin",
  "clientId": "bridge-client-001",
  "accountSnapshot": {
    "secUserId": "MS4wLjABAAAAXXX",
    "platformUid": "123456789",
    "nickname": "夜猫子",
    "profileUrl": "https://www.douyin.com/user/xxx"
  },
  "sessionSnapshot": {
    "cookies": [],
    "localStorage": {},
    "userAgent": "Mozilla/5.0 ..."
  }
}
```

### 服务端处理原则

1. 先认身份，再处理 cookie。
2. 同一 `bridge_client_id` 上报不同 `sec_user_id` 时，不视为普通刷新。
3. 必须判定为“账号切换”。

## 7. 账号绑定与刷新流程

## 7.1 首次绑定流程

1. 前端获取 CookieBridge 在线客户端列表。
2. 用户选择目标客户端。
3. 插件返回身份快照 + 会话快照。
4. 服务端根据 `sec_user_id / identity_value` 查找是否已有账号实体。
5. 若存在，刷新该账号会话。
6. 若不存在，创建新账号实体和会话。
7. 更新 `platform_cookie_bridge_bindings` 来源映射。
8. 派生同步 crawler 兼容表。

## 7.2 已绑定账号刷新流程

1. 插件再次上报身份快照和会话快照。
2. 服务端比对当前账号实体身份。
3. 若身份一致：
   - 更新 session
   - 更新 `cookie_hash`
   - 更新 `last_validated_at`
4. 若身份不一致：
   - 原账号标记为 `account_mismatch`
   - 原 session 标记为 `account_mismatch`
   - 创建或切换到新的账号实体
   - 前端提示“当前浏览器已切换账号”

## 8. 身份校验机制

所有关键动作前必须做轻量身份校验：

1. 刷新作品
2. 发布视频
3. 数据采集任务
4. 定时任务执行前

### 校验流程

1. 使用 `platform_account_sessions` 当前会话访问平台“当前用户信息”接口或页面信息。
2. 提取 `sec_user_id / platform_uid / nickname`。
3. 与 `platform_accounts` 绑定身份比对。

### 校验结果

#### 一致

1. `platform_accounts.account_status = active`
2. `platform_account_sessions.session_status = active`

#### 不一致

1. `platform_accounts.account_status = account_mismatch`
2. `platform_account_sessions.session_status = account_mismatch`
3. 阻断刷新、发布、采集
4. 前端显示“账号已切换，请重新授权”

#### 未登录/接口失效

1. `platform_accounts.account_status = expired`
2. `platform_account_sessions.session_status = expired`
3. 前端显示“登录态失效”

## 9. 采集与发布链路统一策略

## 9.1 发布

发布统一依赖：

1. `platform_accounts`
2. `platform_account_sessions`

并在执行前做身份校验。

## 9.2 采集

采集前先从 `platform_account_sessions` 派生 crawler 所需 cookie。

采集链路不再自己猜账号，只消费已确认身份的账号实体。

## 10. 分发内容列表协同调整

既然一个用户可以有多个抖音账号，则内容表和列表必须带账号维度。

### 当前表

`platform_account_contents`

### 必须保证

1. `account_id` 维度保留。
2. 列表接口返回 `account_id / account_name`。
3. 前端展示账号名。
4. 支持账号筛选。

### 状态建议

1. `published`
2. `pending`
3. `deleted`

### 删除同步策略

刷新时：

1. 本次查到的内容更新为当前状态。
2. 历史存在、本次未查到的内容标记为 `deleted`，而不是直接消失。

## 11. 接口调整建议

## 11.1 保留接口

1. `GET /api/v1/platforms/cookie-bridge/accounts`
2. `POST /api/v1/platforms/cookie-bridge/bind`
3. `GET /api/v1/platforms/accounts`
4. `POST /api/v1/platforms/accounts/{accountId}/sync-self-works`

## 11.2 需要增强的接口

### `POST /api/v1/platforms/cookie-bridge/bind`

请求体增加：

1. `accountSnapshot`
2. `sessionSnapshot`

返回增加：

1. `accountStatus`
2. `identityValue`

### `GET /api/v1/platforms/accounts`

返回增加：

1. `accountStatus`
2. `identityType`
3. `identityValue`
4. `lastIdentityVerifiedAt`
5. `lastIdentityError`

## 11.3 建议新增接口

### `POST /api/v1/platforms/accounts/{accountId}/validate-session`

用途：

1. 手动校验会话身份
2. 更新账号状态

### `POST /api/v1/platforms/accounts/validate-all`

用途：

1. 定时巡检
2. 批量修正授权状态

## 12. 迁移方案

## 12.1 第一阶段：字段扩展

1. 给 `platform_accounts` 增加身份字段和状态字段。
2. 给 `platform_account_sessions` 增加来源字段和校验字段。
3. 给 `platform_cookie_bridge_bindings` 增加最近上报身份字段。

## 12.2 第二阶段：写路径切换

1. 修改 CookieBridge 绑定逻辑，先认身份再写账号。
2. 绑定时同步写新字段。
3. 若旧数据缺少身份字段，则账号状态设为 `needs_rebind`。

## 12.3 第三阶段：读路径切换

1. 发布前先校验身份。
2. 刷新作品前先校验身份。
3. 平台授权页显示真实状态。

## 12.4 第四阶段：兼容表收口

1. crawler 兼容表继续保留一段时间。
2. 改为从主会话表派生。
3. 最终不再单独承担身份定义。

## 13. 最小落地顺序

建议按以下顺序实施：

1. 数据表加字段
2. 绑定接口改成“身份快照 + 会话快照”
3. 账号唯一键切换到稳定身份
4. 刷新/发布前加身份校验
5. 前端平台授权页显示 `active / expired / account_mismatch / needs_rebind`
6. 分发内容页增加账号维度和 deleted 状态
7. 采集与发布都统一走账号实体

## 14. 结论

本次重构不是放弃插件模式，而是重定义插件角色：

1. 插件负责采集浏览器登录态。
2. 服务端负责识别账号身份。
3. 账号实体是稳定真相。
4. 会话只是该账号当前的一份登录状态。

这样即使用户在本地浏览器切号，平台也能自知，不再长期停留在“看起来已授权、实际不可用”的错误状态。
