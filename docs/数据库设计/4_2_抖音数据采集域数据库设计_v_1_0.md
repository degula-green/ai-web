# 4.2 抖音数据采集域数据库设计 v1.0

## 1. 文档说明

本文档用于设计抖音平台的数据采集域数据库结构，覆盖当前阶段的“关键词爬取素材”和“全站热榜采集”两类数据。

当前阶段的目标不是做分析，而是先把采集到的数据稳定保存下来，确保后续可以直接用于：

- 前端展示
- 素材库管理
- 后台 AI 生成输入
- 长期归档与追溯

本次设计重点遵循以下约束：

- 爬虫结果先进入 Redis，作为采集暂存层
- 选择入库后再进入 MySQL，作为长期保存层
- 抖音内容按“图文”和“视频”拆成两张独立表
- 热榜数据独立建表，不与素材表混存
- 原始 JSON 必须保留，避免后续字段扩展时丢失信息

参考资料：

- `legacy/prototypes/tiktok/outputs/COS_图文.json`
- `legacy/prototypes/tiktok/outputs/COS_视频.json`
- `legacy/prototypes/tiktok/outputs/douyin_hot_hot_20260327_172131.json`
- `docs/source_materials/UI设计/4.数据采集/`
- `backend/app/db/mysql/ai_content_automation.sql`
- `docs/数据库设计/4_1_身份权限域数据库设计_v_1_0.docx`

统一命名建议：

- MySQL 表名前缀：`douyin_`
- Redis Key 前缀：`douyin:`
- 主键统一使用 `BIGINT UNSIGNED`
- 时间统一使用 `DATETIME`
- 扩展字段优先使用 `JSON`
- 本设计只保留逻辑引用关系，不创建 MySQL 外键约束

## 2. 设计目标

### 2.1 业务目标

本阶段只做采集与保存，不做内容分析、标签推断、卖点提炼、相似内容检索等增强处理。

系统需要满足以下业务目标：

- 关键词采集结果可稳定落库
- 图文与视频分开存储，便于 UI 展示和后续扩展
- 热榜数据可按天、按批次留存
- 每条数据都能追溯到爬虫任务、采集时间和原始载荷
- 采集数据支持后续 AI 生成模块直接读取

### 2.2 设计原则

- 先暂存，后持久化：Redis 负责临时保存和选择入库，MySQL 负责长期归档
- 结构化字段与原始字段并存：便于展示和排障
- 图文与视频分表：避免一个表同时承担两种内容结构
- 热榜独立存放：避免和素材库混在一起
- 幂等入库：同一条内容重复采集时，以 `platform_source + content_id` 组合键去重
- 兼容扩展：所有不稳定、平台差异大的字段都放入 JSON

说明：

- 本设计中的 `platform_source` 表示内容来源平台标识，抖音场景下固定为 `douyin`
- 主表去重只依赖业务唯一键，不依赖 MySQL 外键约束
- 图文主表和视频主表都采用相同的去重思想，保证同一平台内同一内容只落一份

## 4. 采集与入库流程

### 4.1 流程说明

1. 用户在 UI 中创建关键词采集任务或热榜采集任务
2. 爬虫抓取抖音数据
3. 采集结果先写入 Redis
4. 用户在前端选择“入库”或系统自动确认入库
5. 入库服务从 Redis 读取数据
6. 根据内容类型写入对应的 MySQL 表
7. 入库成功后清理或标记 Redis 中的暂存数据

### 4.2 Redis 的定位

Redis 只承担以下职责：

- 采集结果暂存
- 入库待处理队列
- 去重锁
- 任务进度缓存
- 热榜快照短期缓存

Redis 不作为最终数据源。

### 4.3 MySQL 的定位

MySQL 承担以下职责：

- 长期保存
- 结构化查询
- 素材库展示
- 热榜历史留存
- 后续 AI 生成输入读取

## 5. Redis 设计

### 5.1 Key 规范

建议采用以下 Key 结构：

- `douyin:crawl:item:image:{content_id}`：图文采集暂存
- `douyin:crawl:item:video:{content_id}`：视频采集暂存
- `douyin:crawl:item:hot:{snapshot_no}:{rank}`：热榜采集暂存
- `douyin:crawl:lock:{content_id}`：短时入库去重锁，可选

### 5.2 Redis 数据结构建议

- 单条采集结果使用 `Hash` 或 JSON 字符串
- 去重锁使用 `String + EX`

### 5.3 Redis 生命周期建议

- 图文和视频采集暂存数据默认保留 1 小时
- 用户完成“选择入库”后，相关 Redis 暂存数据立即删除
- 用户在 1 小时内未完成入库选择，暂存数据自动过期清理
- 热榜采集缓存保留 1 小时
- 1 小时后重新抓取热榜，刷新 Redis 与 MySQL 中的最新快照
- 去重锁保留 5 到 30 分钟，仅用于防止短时间重复入库

### 5.4 设计说明

首期不建议引入任务信息缓存、待入库队列和任务统计缓存这类 Redis 结构。

原因如下：

- 任务状态和统计信息可以直接落 MySQL 的 `douyin_crawl_tasks` 表
- 采集结果是高峰期的大头，Redis 应优先用于承接内容暂存，而不是额外保存任务元数据
- 先做“及查即删”的轻量流程，更符合首期只追求采集可用和入库稳定的目标
- 后续如果任务编排、批量重试、断点续传变复杂，再补充队列和统计缓存更合理

因此，当前阶段 Redis 只保留两类核心职责：

- 采集内容暂存
- 短时去重控制

## 7. 表设计

### 7.1 `douyin_crawl_tasks` 采集任务表

用途：

- 记录每次关键词采集、热榜采集的任务基础信息
- 记录任务生命周期、采集进度和异常信息
- 为 Redis 队列和 MySQL 入库提供统一的任务编号

字段设计：

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 |
| `task_no` | VARCHAR(64) | 任务编号，业务唯一 |
| `platform` | VARCHAR(32) | 平台来源标识，固定 `douyin`，用于组成 `platform_source + content_id` 去重键 |
| `task_type` | VARCHAR(32) | 任务类型，如 `keyword`、`hot` |
| `keyword` | VARCHAR(128) | 采集关键词，热榜任务可为空 |
| `content_kind` | VARCHAR(16) | 内容类型，如 `image`、`video`、`all` |
| `board_type` | VARCHAR(32) | 榜单类型，如 `hot`、`search_hot` |
| `crawl_mode` | VARCHAR(32) | 采集模式，如 `manual`、`scheduled` |
| `owner_user_id` | BIGINT UNSIGNED | 归属用户 ID，引用 `iam_users.id` |
| `source_config_json` | JSON | 采集配置，如分页、排序、过滤条件 |
| `task_status` | VARCHAR(32) | 任务状态，如 `pending`、`running`、`success`、`failed`、`paused` |
| `total_count` | INT | 计划采集总数 |
| `pending_count` | INT | 待入库数量 |
| `imported_count` | INT | 已入库数量 |
| `fail_count` | INT | 失败数量 |
| `started_at` | DATETIME | 开始时间 |
| `finished_at` | DATETIME | 完成时间 |
| `last_error` | VARCHAR(1000) | 最近一次错误信息 |
| `operator_id` | BIGINT UNSIGNED | 操作人 ID，引用系统用户 |
| `remark` | VARCHAR(500) | 备注 |
| `created_at` | DATETIME | 创建时间 |
| `updated_at` | DATETIME | 更新时间 |

索引建议：

- `uk_task_no`：`task_no` 唯一索引
- `idx_platform_type`：`platform + task_type`
- `idx_owner_user_id`：`owner_user_id`
- `idx_task_status`：`task_status`
- `idx_keyword`：`keyword`
- `idx_created_at`：`created_at`

### 7.2 `douyin_user_material_chain` 用户素材链表

用途：

- 建立系统登录用户与图文/视频素材之间的归属链路
- 作为素材列表页的直接查询表
- 避免列表页每次都先扫主表再回表取用户归属信息
- 支持按 `owner_user_id` 直接查看该用户名下的图文和视频素材

这个表不是给平台作者用的，也不是热榜表。它描述的是“哪个系统用户收藏/入库了哪条抖音素材”。

字段设计：

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT UNSIGNED | 主键 |
| `owner_user_id` | BIGINT UNSIGNED | 归属用户 ID，引用 `iam_users.id` |
| `content_kind` | VARCHAR(16) | 内容类型，`image` 或 `video` |
| `material_id` | BIGINT UNSIGNED | 主表 ID，指向图文或视频素材表 |
| `task_id` | BIGINT UNSIGNED | 任务 ID，引用 `douyin_crawl_tasks.id` |
| `content_id` | VARCHAR(64) | 抖音内容 ID，冗余保存，便于快速定位 |
| `title` | VARCHAR(500) | 列表展示标题 |
| `cover_url` | VARCHAR(1024) | 列表展示封面 |
| `publish_at` | DATETIME | 发布时间 |
| `like_count` | BIGINT | 点赞数，列表展示用 |
| `comment_count` | BIGINT | 评论数，列表展示用 |
| `collect_count` | BIGINT | 收藏数，列表展示用 |
| `share_count` | BIGINT | 转发数，列表展示用 |
| `chain_status` | VARCHAR(32) | 链路状态，如 `active`、`removed`、`archived` |
| `linked_at` | DATETIME | 归属关系建立时间 |
| `remark` | VARCHAR(500) | 备注 |
| `created_at` | DATETIME | 创建时间 |
| `updated_at` | DATETIME | 更新时间 |

索引建议：

- `uk_owner_kind_material`：`owner_user_id + content_kind + material_id` 唯一索引
- `idx_owner_kind_time`：`owner_user_id + content_kind + linked_at`
- `idx_task_id`：`task_id`
- `idx_content_id`：`content_id`

说明：

- 用户素材列表页只查这张链表，不直接查图文/视频主表
- 链表已经保存了列表页所需的摘要字段，因此可以直接展示
- 详情页再根据 `material_id` 回主表读取完整原始数据
- 这样可以把“按用户看素材”的高频查询和“按素材看详情”的低频查询拆开

## 8. 关系设计

### 8.1 任务与素材关系

- `iam_users` 1 对多 `douyin_crawl_tasks`
- `iam_users` 1 对多 `douyin_user_material_chain`
- `douyin_crawl_tasks` 1 对多 `douyin_image_materials`
- `douyin_crawl_tasks` 1 对多 `douyin_video_materials`
- `douyin_crawl_tasks` 1 对多 `douyin_hot_rank_items`

### 8.2 用户与素材关系

- `douyin_user_material_chain` 是用户与图文/视频主表之间的中间链路
- `iam_users` 通过 `douyin_user_material_chain.owner_user_id` 逻辑上定位到用户素材列表
- 图文/视频主表不再承担“按登录用户查列表”的职责
- 素材表中的 `author_id`、`author_name` 表示抖音内容源作者
- 查询“某个登录用户下的素材”时，先查 `douyin_user_material_chain`
- 查询单条素材详情时，再根据 `material_id` 回主表取完整原始数据

### 8.3 任务与 Redis 关系

- 一个任务对应一个 Redis 任务上下文
- 每条采集结果先写 Redis，再选择入库
- 入库完成后可删除 Redis 暂存记录，或保留短期审计信息

### 8.4 数据去重原则

- 图文与视频主表分别按 `platform_source + content_id` 去重
- 用户素材链按 `owner_user_id + content_kind + material_id` 去重
- 热榜按 `platform_source + board_type + snapshot_no + rank` 去重
- Redis 入库前使用短锁防止重复写库

## 9. 字段保留策略

### 9.1 必须保留的字段

以下字段必须长期保存：

- 内容 ID
- 作者信息
- 标题与描述
- 发布时间
- 互动数据
- 封面图与主媒体地址
- 关键词
- 任务编号
- 采集时间
- 原始 JSON

### 9.2 建议保留的扩展字段

以下字段建议保留在 `extra_json` 或 `raw_json` 中：

- 图片列表或视频多规格地址
- 分享信息
- 标签与话题列表
- 音乐信息
- 地理位置
- 视频控制字段
- 作者原始详情
- 热榜原始附加字段

## 10. 首期实现边界

本阶段只实现以下能力：

- 抖音图文采集
- 抖音视频采集
- 抖音热榜采集
- Redis 暂存
- 选择入库
- MySQL 长期存储

本阶段不实现以下能力：

- 内容分析
- 卖点提炼
- 标签智能生成
- 相似内容检索
- 热榜趋势分析
- AI 自动归因

## 11. 后续可扩展方向

如果后续需要继续扩展，建议按以下方向推进：

- 补充素材审核状态字段
- 增加素材入库来源和人工确认人信息
- 将 `media_json` 拆成图片/视频子表
- 增加热榜快照头表，支持整批榜单版本管理
- 增加采集失败日志表和重试日志表
- 增加入库变更记录表，支持回滚与审计

## 12. 结论

本设计将抖音采集数据拆分为四个核心对象：

- 采集任务
- 图文素材
- 视频素材
- 热榜数据

同时通过 Redis 作为采集暂存层、MySQL 作为长期保存层，确保数据结构既能满足当前 UI 展示，也能为后续 AI 生成模块提供稳定输入。
