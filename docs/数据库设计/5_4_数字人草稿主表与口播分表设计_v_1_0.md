# 5.4 数字人草稿主表与口播分表设计 v1.0

## 1. 文档说明

本文档用于重构当前数字人草稿模型，目标是将现有“单表混合存储”的草稿结构，调整为：

- 1 张数字人草稿主表
- N 张按场景拆分的草稿分表

本阶段只落地：

1. 新建数字人草稿主表 `avatar_drafts`
2. 将当前 `creation_drafts` 收口为“口播数字人草稿分表”
3. 调整草稿列表、草稿详情、草稿保存的查询与写入路径

本阶段**不设计**：

- 卖货数字人分表
- 产品介绍数字人分表
- 模特数字人分表
- 所有未来场景的完整字段

原因是这些流程尚未完全跑通，业务字段仍在变动，不适合提前固化。

---

## 2. 重构背景

当前数字人草稿存在以下问题：

1. `creation_drafts` 同时承载通用草稿与不同场景数据，语义混杂。
2. 场景识别依赖 `content_info` / `digital_human_params` 中的字段推断，前后端容易出现误判。
3. 草稿箱查询虽然只按用户拉取，但前端还要二次解析场景，容易出现跨场景混用。
4. 未来卖货、产品介绍、模特数字人需要不同流程和参数，继续往当前结构里塞字段会越来越难维护。

因此，本次重构采用：

- **主表负责索引和定位**
- **分表负责场景业务数据**

该结构的核心目标是：

- 按用户和场景快速定位草稿
- 保证不同场景的字段不混放
- 为前端后续模块化拼装提供稳定的数据边界

---

## 3. 设计原则

### 3.1 主表只做索引，不做业务承载

主表只存：

- 这是谁的草稿
- 这是什么场景的草稿
- 标题、状态、时间等列表级信息

主表不存：

- 文案正文
- 音色参数
- 数字人生成参数
- 剪辑参数

### 3.2 场景分表只存本场景数据

每个场景一张表：

- 口播数字人只写口播分表
- 卖货数字人以后只写卖货分表
- 模特数字人以后只写模特分表

不允许继续把未来场景字段混塞到通用 JSON 里。

### 3.3 列表先查主表，详情再查分表

草稿箱展示流程统一为：

1. 先查主表
2. 主表返回 `scene_code`
3. 根据 `scene_code` 查询对应分表详情

### 3.4 先收口口播场景，不一次性铺开全部分表

本阶段仅把当前 `creation_drafts` 定位为 `talk` 场景的业务承载表，后续新场景再逐个落地。

| 表名 | 用途 | 说明 |
| --- | --- | --- |
| `avatar_drafts` | 数字人草稿主表 | 存草稿索引信息，支持按用户/场景查询 |
| `creation_drafts` | 口播数字人草稿分表（过渡阶段） | 暂继续使用现有物理表，代码语义调整为 `talk` 场景分表 |

说明：

- 本阶段为了降低改造风险，**暂不强制改物理表名**。

- 后续条件成熟后，再迁移为正式表名 `avatar_draft_talk`。

## 5. 主表设计：`avatar_drafts`

### 5.1 表用途

统一管理所有数字人场景的草稿索引信息，用于：

- 草稿箱列表查询
- 按场景过滤
- 草稿恢复入口
- 草稿状态展示

### 5.2 字段设计

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `draft_id` | VARCHAR(64) | 草稿主键，统一草稿ID |
| `user_id` | BIGINT UNSIGNED | 所属用户ID |
| `scene_code` | VARCHAR(32) | 场景编码：`talk` / `sales` / `product` / `model` |
| `title` | VARCHAR(255) | 草稿标题，用于列表展示 |
| `status` | VARCHAR(32) | 草稿状态：`draft` / `rewritten` / `video_generating` / `completed` / `failed` 等 |
| `current_step_code` | VARCHAR(64) | 当前流程所处步骤编码 |
| `progress` | INT | 当前进度，可选，范围建议 0-100 |
| `is_deleted` | TINYINT(1) | 逻辑删除标记：0否，1是 |
| `created_at` | DATETIME | 创建时间 |
| `updated_at` | DATETIME | 更新时间 |

### 5.3 建表建议 SQL

```sql
CREATE TABLE IF NOT EXISTS avatar_drafts (
    draft_id VARCHAR(64) PRIMARY KEY COMMENT '草稿ID，数字人草稿全局唯一主键',
    user_id BIGINT UNSIGNED NOT NULL COMMENT '所属用户ID',
    scene_code VARCHAR(32) NOT NULL COMMENT '数字人场景编码，如 talk/sales/product/model',
    title VARCHAR(255) NULL COMMENT '草稿标题，用于草稿箱列表展示',
    status VARCHAR(32) NOT NULL DEFAULT 'draft' COMMENT '草稿状态，如 draft/rewritten/video_generating/completed/failed',
    current_step_code VARCHAR(64) NULL COMMENT '当前流程步骤编码，用于前端恢复当前所处模块',
    progress INT NULL COMMENT '当前流程进度，建议范围 0-100',
    is_deleted TINYINT(1) NOT NULL DEFAULT 0 COMMENT '逻辑删除标记：0未删除，1已删除',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    KEY idx_avatar_drafts_user_scene_updated (user_id, scene_code, updated_at),
    KEY idx_avatar_drafts_user_updated (user_id, updated_at),
    KEY idx_avatar_drafts_scene_status (scene_code, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='数字人草稿主表，负责统一记录用户草稿索引信息';
```

### 5.4 场景编码建议

| 场景名称 | scene_code |
| --- | --- |
| 口播数字人 | `talk` |
| 卖货数字人 | `sales` |
| 产品介绍数字人 | `product` |
| 模特数字人 | `model` |

本阶段只实际启用：

- `talk`

## 6. 口播分表设计：`creation_drafts`

### 6.1 本阶段定位

当前 `creation_drafts` 物理表暂不删除、不改名，但从代码语义上调整为：

> 口播数字人草稿分表（`talk` 场景分表）

### 6.2 表用途

承载口播数字人的全部业务数据，包括：

- 视频分析结果
- 文案提取结果
- 文案改写结果
- 声音参数
- 数字人参数
- 剪辑参数

### 6.3 与主表关系

- `avatar_drafts.draft_id = creation_drafts.id`
- 关系为 1:1

约束要求：

1. 主表先存在
2. `creation_drafts` 只允许存 `talk` 场景的数据
3. 不再允许模特、卖货等场景继续写入该表

### 6.4 当前表结构继续保留的字段

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `id` | VARCHAR(64) | 草稿ID，对应主表 `draft_id` |
| `user_id` | BIGINT | 当前用户ID |
| `title` | VARCHAR(255) | 草稿标题 |
| `source_url` | VARCHAR(1024) | 原始视频链接 |
| `platform` | VARCHAR(64) | 平台编码 |
| `content_id` | VARCHAR(255) | 内容ID |
| `content_info` | JSON | 内容补充信息 |
| `transcript` | JSON | 转录结果 |
| `extracted_copy` | TEXT | 提取文案 |
| `rewrite_instruction` | TEXT | 改写指令 |
| `rewritten_copy` | TEXT | 改写结果 |
| `voice_params` | JSON | 声音生成参数 |
| `digital_human_params` | JSON | 数字人生成参数 |
| `clip_params` | JSON | 剪辑参数 |
| `status` | VARCHAR(32) | 状态 |
| `created_at` | DATETIME | 创建时间 |
| `updated_at` | DATETIME | 更新时间 |

### 6.5 本阶段对 `creation_drafts` 的约束调整

本阶段不强制拆散 `voice_params` / `digital_human_params` / `clip_params` 中的 JSON 字段，原因如下：

1. 当前口播流程已可用，继续保留 JSON 可以降低改动范围
2. 本阶段目标是先完成主表+分表边界梳理
3. 等口播场景后续稳定后，再决定是否进一步结构化字段

## 7. 当前数据库改造方案

### 7.1 推荐策略

本阶段采用：

- **新增主表**
- **保留现有 `creation_drafts` 作为口播分表**
- **代码层切换查询与写入路径**

### 7.2 改造步骤

#### 第一步：新增 `avatar_drafts`

上线主表，不影响现有 `creation_drafts` 使用。

#### 第二步：为现有 `creation_drafts` 回填主表记录

对现有口播草稿数据进行一次初始化迁移：

- `avatar_drafts.draft_id = creation_drafts.id`
- `avatar_drafts.user_id = creation_drafts.user_id`
- `avatar_drafts.scene_code = 'talk'`
- `avatar_drafts.title = creation_drafts.title`
- `avatar_drafts.status = creation_drafts.status`
- `avatar_drafts.created_at = creation_drafts.created_at`
- `avatar_drafts.updated_at = creation_drafts.updated_at`

#### 第三步：后续口播草稿双写

口播页创建或保存草稿时：

1. 写主表
2. 写 `creation_drafts`

#### 第四步：禁止非口播场景继续写 `creation_drafts`

卖货、产品、模特场景后续需要单独分表，不再复用当前表。

## 8. 迁移 SQL 参考

### 8.1 主表初始化插入

```sql
-- 将现有 creation_drafts 中的历史口播草稿回填到数字人草稿主表
-- 约定当前 creation_drafts 中的数据全部视为 talk 场景
INSERT INTO avatar_drafts (
    draft_id,
    user_id,
    scene_code,
    title,
    status,
    created_at,
    updated_at
)
SELECT
    id AS draft_id,          -- 原草稿ID映射为主表草稿ID
    user_id,                 -- 原所属用户ID
    'talk' AS scene_code,    -- 本阶段统一回填为口播数字人场景
    title,                   -- 草稿标题
    status,                  -- 草稿状态
    created_at,              -- 原创建时间
    updated_at               -- 原更新时间
FROM creation_drafts
WHERE NOT EXISTS (
    SELECT 1
    FROM avatar_drafts ad
    WHERE ad.draft_id = creation_drafts.id  -- 避免重复回填
);
```

### 8.2 后续可选唯一性约束建议

如果系统约束草稿ID全局唯一，则主表中只需要 `draft_id` 主键即可。  
如果后续考虑更强数据约束，可在分表侧确保：

```sql
-- 可选：为当前口播分表补充唯一约束，确保草稿ID在分表中唯一
ALTER TABLE creation_drafts
ADD CONSTRAINT uq_creation_drafts_id UNIQUE (id);
```

### 8.3 后续正式切换为 `avatar_draft_talk` 的建表模板

当口播分表准备从 `creation_drafts` 正式迁移为 `avatar_draft_talk` 时，可参考以下建表 SQL：

```sql
CREATE TABLE IF NOT EXISTS avatar_draft_talk (
    draft_id VARCHAR(64) PRIMARY KEY COMMENT '口播数字人草稿ID，对应主表 draft_id',
    user_id BIGINT UNSIGNED NOT NULL COMMENT '所属用户ID，保留冗余便于审计与排查',
    source_url VARCHAR(1024) NULL COMMENT '原始视频或内容链接',
    platform VARCHAR(64) NULL COMMENT '来源平台编码，如 douyin/xiaohongshu/bilibili/ks',
    content_id VARCHAR(255) NULL COMMENT '来源内容ID',
    content_info JSON NOT NULL COMMENT '内容扩展信息，如标题、作者、平台补充字段',
    transcript JSON NOT NULL COMMENT '转录结果，如 ASR 文本、分段、时间轴',
    extracted_copy TEXT NULL COMMENT '提取后的原始文案',
    rewrite_instruction TEXT NULL COMMENT '文案改写指令',
    rewritten_copy TEXT NULL COMMENT '改写后的口播文案',
    voice_params JSON NOT NULL COMMENT '声音生成参数，如音色、语速、音量、音频地址',
    digital_human_params JSON NOT NULL COMMENT '数字人生成参数，如形象素材、任务ID、生成视频地址',
    clip_params JSON NOT NULL COMMENT '剪辑参数，如字幕样式、背景素材、BGM、成片信息',
    status VARCHAR(32) NOT NULL DEFAULT 'draft' COMMENT '口播场景分表内部状态',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    KEY idx_avatar_draft_talk_user_updated (user_id, updated_at),
    CONSTRAINT fk_avatar_draft_talk_draft_id
        FOREIGN KEY (draft_id) REFERENCES avatar_drafts(draft_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='口播数字人草稿分表，承载口播场景完整业务数据';
```

## 9. 接口重构方案

本阶段不要求大规模重写 API，只调整查询职责。

### 9.1 草稿列表接口

建议新增：

`GET /api/v1/avatar-drafts?scene=talk&limit=20&offset=0`

返回内容只包含主表信息：

```json
{
  "items": [
    {
      "draft_id": "draft_xxx",
      "scene_code": "talk",
      "title": "提取文案后，可继续生成视频标题",
      "status": "draft",
      "updated_at": "2026-05-06T09:34:00"
    }
  ]
}
```

#### 列表接口职责

- 只查主表
- 默认按 `user_id + scene_code`
- 按 `updated_at desc` 排序

### 9.2 草稿详情接口

建议改造为：

`GET /api/v1/avatar-drafts/{draft_id}`

后端处理流程：

1. 查 `avatar_drafts`
2. 读取 `scene_code`
3. 如果 `scene_code = talk`
4. 再查 `creation_drafts`
5. 返回口播草稿详情结构

### 9.3 草稿保存接口

建议改造为：

- `POST /api/v1/avatar-drafts`
- `PATCH /api/v1/avatar-drafts/{draft_id}`

后端处理流程：

1. 根据当前场景先写主表
2. 如果当前场景是 `talk`，再写 `creation_drafts`

### 9.4 删除接口

建议删除时同步处理：

1. 逻辑删除主表，或直接物理删除
2. 删除对应分表记录

## 10. 前端查询与保存流程调整

### 10.1 草稿箱列表

当前数字人前端页面不应再直接调用：

`/api/v1/creation-drafts`

而应切换为：

`/api/v1/avatar-drafts?scene=talk`

这样口播页只拿口播草稿列表，不再在前端二次推断场景。

### 10.2 草稿详情恢复

点击草稿项时：

1. 先通过 `draft_id` 调主草稿详情接口
2. 后端根据 `scene_code` 路由到正确分表
3. 前端直接接收该场景的标准返回

### 10.3 当前前端页的短期策略

本阶段建议：

- 口播数字人页先接主表+口播分表
- 模特页暂继续使用现有逻辑，但不要继续写入 `creation_drafts`
- 卖货、产品介绍页如果尚未完整跑通，先不要接主表迁移

## 11. 与现有系统的兼容要求

### 11.1 兼容旧草稿数据

必须支持从现有 `creation_drafts` 数据中回填主表，避免历史草稿丢失。

### 11.2 兼容现有草稿ID

`draft_id` 必须延续当前草稿ID，不重新生成，避免：

- 前端旧链接失效
- 任务中心中的 `draftId` 丢失对应关系

### 11.3 兼容现有口播接口参数

本阶段不要求口播场景字段彻底重构，只要求：

- 查询路径正确
- 写入边界清晰
- 数据不再被其他场景混用

## 14. 补充决策：一场景一页面 + 一场景一分表

### 14.1 前端设计调整

基于当前数字人业务已经出现明显分化：

- 口播数字人
- 卖货数字人
- 产品介绍数字人
- 模特数字人

它们的步骤顺序、表单字段、任务类型、结果形态并不一致。继续强行维护一个通用页面，会导致：

1. 页面内部 `if/else` 与条件渲染越来越多
2. 不同场景之间互相污染状态
3. 草稿恢复逻辑越来越复杂
4. 后续扩展新场景时改动面过大

因此，后续建议正式收敛为：

- **一个场景一个单独页面**
- **一个场景一张单独分表**
- **主表只负责草稿索引与场景定位**

即：

| 场景 | 页面 | 分表 |
| --- | --- | --- |
| 口播数字人 | `CreationAvatarTalkView.vue` | `avatar_draft_talk` |
| 卖货数字人 | `CreationAvatarSalesView.vue` | `avatar_draft_sales` |
| 产品介绍数字人 | `CreationAvatarProductView.vue` | `avatar_draft_product` |
| 模特数字人 | `CreationAvatarModelView.vue` | `avatar_draft_model` |

---

### 14.2 数据库目标结构

| 表名 | 作用 | 说明 |
| --- | --- | --- |
| `avatar_drafts` | 数字人草稿主表 | 统一存索引信息，不存具体业务明细 |
| `avatar_draft_talk` | 口播分表 | 存口播数字人的完整业务数据 |
| `avatar_draft_sales` | 卖货分表 | 后续落地 |
| `avatar_draft_product` | 产品介绍分表 | 后续落地 |
| `avatar_draft_model` | 模特分表 | 存模特图组生成类业务数据 |

说明：

- `creation_drafts` 不再建议继续作为长期正式表名
- 过渡期可以先把它迁移为 `avatar_draft_talk`
- 后续代码全部围绕正式分表名开发

---

### 14.3 主表最终建议 SQL

```sql
CREATE TABLE IF NOT EXISTS avatar_drafts (
    draft_id VARCHAR(64) NOT NULL COMMENT '草稿ID，所有数字人场景共享的业务主键',
    user_id BIGINT UNSIGNED NOT NULL COMMENT '所属用户ID',
    scene_code VARCHAR(32) NOT NULL COMMENT '场景编码：talk/sales/product/model',
    title VARCHAR(255) NULL COMMENT '草稿标题',
    status VARCHAR(32) NOT NULL DEFAULT 'draft' COMMENT '草稿状态，如 draft/rewritten/completed/failed',
```

### 14.7 针对当前“口播被误写成模特”的修复 SQL

### 14.8 本次方案的最终结论

数据库与前端后续统一按下述原则推进：

1. **一场景一页面**
2. **一场景一分表**
3. **主表只存索引，不存业务明细**
4. **草稿场景一旦创建成功，不允许后续修改**
5. **任何草稿恢复，都必须先查主表场景，再进入对应页面和分表**

这个方案比“一个通用数字人页面 + 多场景分支判断”更稳，也更适合后面继续加卖货、产品介绍、模特等不同工作流。
